1. System Architecture

Two-Dimensional System Flow

User Request │ ▼ Authentication │ ▼ User Identity │ ▼ User Role/RBAC │ ▼ LangGraph Agent │ ▼ Tool Selection │ ▼ Permission Check │ ┌───────┴───────┐ │ │ Allowed Denied │ │ ▼ ▼ Execute Tool Explain Access │ ▼ Tool Result │ ▼ Need More Tools? / \ Yes No │ │ └──► Agent │ ▼ Response

Core Architecture Components

  • Authentication Layer: FastAPI JWT validation
  • Authorization Layer: Role-Based Access Control (RBAC)
  • Orchestration Layer: LangGraph agent supervision
  • Tool Execution Layer: Permission-aware tool execution
  • Data Layer: PostgreSQL database
  • Intelligence Layer: RAG system and policy retrieval

3. Role-Based Access Control (RBAC)

⚠️ Critical Design Principle: The AI agent itself must understand permissions. This is not just an API-level protection.

Example: Denied Access Scenario

Patient asks: "Show me all patients who have appointments tomorrow." LLM decides: Appointment Search Tool Tool Request ↓ Permission Manager ↓ User = PATIENT ↓ Requested Scope = ALL PATIENTS ↓ ❌ DENIED

Result: The tool never executes. The agent responds with an access denial message.

4. Scope-Based Permissions

Permission Levels

Role Tool Access Scope
Patient appointment_tool OWN_DATA
Receptionist appointment_tool ALL_PATIENTS
Billing billing_tool FINANCIAL_DATA
Administrator all_tools FULL_SYSTEM

Examples

Patient:

  • ✅ "What appointments do I have tomorrow?" — Allowed
  • ❌ "What appointments does P1004 have tomorrow?" — Denied (if P1004 ≠ current user)

Receptionist:

  • ✅ "What appointments does P1004 have tomorrow?" — Allowed

5. Appointment Booking Workflow

Stateful Workflow Process

User Request ↓ Agent Understanding ↓ Identify Doctor ↓ Check Doctor Schedule ↓ Find Available Slots ↓ Ask User to Select Slot ↓ Confirm Booking ↓ Create Appointment ↓ Send Confirmation

Example Conversation Flow

User: "I want to book an appointment with Dr. Ahmed."

Agent: "Sure. What date would you prefer?"

User: "Next Monday."

Agent: (Internal: Calendar Tool → Doctor Schedule Tool → Available Slots)

Agent: "Dr. Ahmed has these available slots:

  • 10:00 AM
  • 11:30 AM
  • 2:00 PM

Which one would you like?"

User: "11:30 AM."

Agent: (Does not immediately book)

Agent: "Please confirm:

Dr. Ahmed — Monday, 11:30 AM

Would you like me to book this appointment?"

User: "Yes."

Agent: (Internal: Appointment Tool → Create Appointment → Notification Tool → Confirmation)

Slot Unavailability Handling

User selects 11:30 AM ↓ Agent checks slot ↓ Someone else booked it ↓ Appointment Tool ↓ ❌ Slot unavailable

Agent Response: "Unfortunately, the 11:30 AM slot is no longer available. The next available slots are 1:00 PM and 2:30 PM. Would you like one of these?"

6. Rescheduling & Cancellation

Rescheduling Workflow

"Move my appointment to Wednesday." ↓ Get Current Appointment ↓ Get Doctor Schedule ↓ Check Wednesday Availability ↓ Present Slots ↓ User Selects ↓ Confirmation ↓ Reschedule Appointment ↓ Notification

Cancellation Workflow

"Cancel my appointment tomorrow." ↓ Appointment Tool ↓ Find user's appointment ↓ Cancellation Policy RAG ↓ Check policy ↓ Ask confirmation ↓ Cancel ↓ Notification
Key Insight: This demonstrates multi-tool behavior:
  1. Appointment Tool
  2. Policy RAG
  3. Notification Tool

7. Policy RAG Integration

Policy-Aware Decision Making

Example Policy: "Appointments can be cancelled without penalty up to 24 hours before the appointment."

User Question: "Can I cancel my appointment?"

Agent Process:

Policy RAG ↓ Cancellation Policy ↓ Appointment Tool ↓ Check appointment time ↓ Determine eligibility

Principle: The LLM doesn't invent the policy. It retrieves and applies actual policies.

12. User Experience Scenarios

Patient Experience

User: "I want to see Dr. Ahmed next Tuesday."

Agent Process:

Doctor Search ↓ Schedule ↓ Availability

Agent Response: "Dr. Ahmed has availability at 10:00 AM, 1:00 PM, and 3:30 PM."

User: "Book 1 PM."

Agent Process:

Permission Check ↓ PATIENT ↓ Own appointment ↓ ✅ Allowed ↓ Create Appointment

Receptionist Experience

Receptionist: "Book P1004 with Dr. Ahmed at 1 PM."

Agent Process:

Permission Check ↓ RECEPTIONIST ↓ Can manage patient appointments ↓ ✅ Allowed ↓ Book

Access Denied Scenario

Patient: "Show me P1004's appointments."

Agent Process:

Agent ↓ Appointment Tool ↓ Permission Engine ↓ PATIENT ↓ Target = P1004 ↓ Current User ≠ P1004 ↓ ❌ DENIED

Agent Response: "I'm sorry, but you don't have permission to view other patients' appointments."

13. Three Types of Intelligence

1. LLM Intelligence

Understanding natural language and converting to structured requirements:

User: "Can I see the doctor sometime Tuesday afternoon?"

LLM Conversion:

doctor = unknown date = Tuesday time_range = afternoon action = appointment_search

2. Agent Intelligence

Determining the execution plan:

Need doctor search → Need schedule → Need availability

3. Backend Intelligence

Determining permissions:

Is this user allowed to perform this operation?
Key Principle: The system does not rely on the LLM for everything. Each layer has its own intelligence.

14. Critical Design Principles

❌ Don't Let the LLM Decide Permissions

Bad Architecture:

LLM: "This user looks like an admin, so I'll allow it."

Good Architecture:

LLM ↓ Requests Tool ↓ Backend Permission Layer ↓ RBAC Check ↓ Allowed / Denied

Principle: The LLM can request an action. The backend decides whether it is permitted.
